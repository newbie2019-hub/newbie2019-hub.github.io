3:T1f02,<p>AI changed the shape of my work, not the responsibility attached to it. I still
own the architecture, the trade-offs and whatever ships. What changed is how
much of the day goes into typing versus thinking — and the tooling below exists
to shift that ratio as far toward thinking as it will go.</p>
<h2>Planning comes before prompting</h2>
<p>The single biggest determinant of output quality isn&#39;t the model. It&#39;s how well
the problem was specified before the model saw it.</p>
<p>Ahead of any implementation I write the problem statement, the user stories with
their acceptance criteria, the UI flow including the empty and error states, and
an explicit out-of-scope list. Then the tests, against those acceptance criteria,
before the implementation exists.</p>
<p>That last one matters more than it sounds. A failing test is an unambiguous
specification — it either passes or it doesn&#39;t. Given one, a model writes toward
a target rather than toward something that merely looks plausible. Given a vague
paragraph instead, it will confidently build the wrong thing and the code will
compile perfectly while doing so. Most of what gets called &quot;AI slop&quot; is really a
planning failure that arrived at speed.</p>

</ul><h2>How a feature actually moves</h2>
<ol>
<li><strong>Specify.</strong> Problem statement, stories, acceptance criteria, scope boundary.</li>
<li><strong>Design the flow.</strong> Screens and states, so there&#39;s something concrete to
build against rather than a description to imagine.</li>
<li><strong>Write the tests.</strong> Red first, straight from the acceptance criteria.</li>
<li><strong>Delegate the implementation.</strong> Claude in a Herdr pane, dictated where
dictating is faster. Cursor when the change is easier to point at than to
describe.</li>
<li><strong>Review properly.</strong> Every diff read as though a contractor wrote it, because
in effect one did. Speed of generation is not a reason to lower the bar for
what gets merged.</li>
<li><strong>Ship, then watch it.</strong> Monitoring and error tracking, because the failure
modes that matter only ever surface in production.</li>
</ol>
<h2>What this is actually for</h2>
<p>None of this is about writing less code. It&#39;s about spending a larger share of
the day on the decisions that are genuinely hard — the data model, the boundary
between systems, what happens when the third-party API times out — and a smaller
share on the mechanical work that surrounds them.</p>
<p>The engineering judgement is still mine. The typing no longer has to be.</p>
